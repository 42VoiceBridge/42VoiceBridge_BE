## 0. 한 줄 요약

| # | 기능 | 한 줄 설명 | 새 외부 API | 크기 |
| --- | --- | --- | --- | --- |
| A | 말해서 문구 추가 | 말 → 인식 → 내가 고침 → 문구로 저장. 이후엔 인식 없이 정확하게 말함 | 없음 | 작음 |
| B | 문장 확장·문구 추천 | 짧게 말하거나 상황을 적으면 문장 후보를 제안, 내가 골라서 저장·확인 | LLM | 작음~중간 |

주제 적합성: 모두 "AI가 구음장애 사용자의 말하기를 보조한다"는 방향이고, A와 B는 사용자가 확인한 문장만 말한다는 기존 원칙(AI 계약 D5)을 그대로 지킨다.

## 1. 공통 원칙

1. **AI가 만든 문장은 사용자가 고르고 확인해야만 말한다.** 자동 TTS 없음.
2. **LLM·음성인식이 죽어도 문구 저장과 말하기는 동작한다.** 이 기능들은 전부 선택 기능이고, 실패하면 503과 안내 문구만 나간다.
3. **기능마다 설정 플래그로 켠다(기본 꺼짐).** `voicebridge.features.suggestion`, `voicebridge.features.conversation`. A는 새 백엔드 코드가 거의 없어 플래그가 필요 없다.
4. **키는 환경변수로만 받는다.** 코드·`application.yml`에 값을 쓰지 않는다(CLAUDE.md 9장).
5. **입력 텍스트·음성은 로그에 남기지 않고, 앱에 외부 전송 고지를 한다.** 음성과 문구는 민감정보다.
6. 외부 호출은 `@Transactional` 밖에서 한다. 포트(`port/out`)에는 외부 SDK 타입을 노출하지 않는다.

## 2. 기능 A — 말해서 문구 추가

**흐름**: `POST /recognitions`(기존) → 사용자가 결과를 고침 → `POST /recognitions/{id}/confirm`(기존) → "문구로 저장" → `POST /phrases`(PR 2) `{category, text}`.

**백엔드 변경: 사실상 없음.** 프론트가 확인된 텍스트를 `POST /phrases`로 보내면 끝난다.
- 선택 사항(YAGNI로 이번엔 제외): `confirmationId`를 같이 받아 "인식에서 온 문구"를 표시.
- 인식(Recognition)은 배포된 AI 서버(2026-10-30 health 확인, 기본 Whisper-small)를 쓴다. AI 서버가 바쁘거나 내려가 인식이 503이어도 문구는 타이핑으로 추가하면 되므로 서비스는 막히지 않는다.

**왜 가치가 큰가**: 인식은 틀릴 수 있다. 한 번 고쳐서 저장한 문장은 이후 인식 없이 정확하게 말한다. 모델의 약점을 사용 방식으로 메운다.

**테스트**: 백엔드 신규 없음. 프론트 E2E에서 "인식 → 수정 → 저장 → 문구 목록에 나타남 → 말하기"를 수동 확인한다.

## 3. 기능 B — 문장 확장·문구 추천

### 3.1 API

`POST /api/v1/phrases/suggestions` (JWT 필요, 플래그 `suggestion`이 꺼져 있으면 404)

요청: `{ "text": "물", "category": "RESTAURANT" }` (`category`는 선택)
응답: `{ "candidates": ["물 좀 주세요.", "물 한 잔 주세요."] }`

- 입력이 짧은 발화("물")든 상황 키워드("병원 접수")든 같은 프롬프트로 처리한다. 모드를 나누지 않는다(YAGNI).
- 후보는 저장하지 않는다. 사용자가 고르면 기존 `POST /phrases`로 저장하거나, 인식 흐름이면 기존 확인 API를 탄다.

### 3.2 구성

- `port/in/SuggestPhrasesUseCase`
- `port/out/LlmSuggestionPort`: 메서드 `expand(String text, PhraseCategory category)`. 대화 모드와 같은 포트를 쓰고 메서드만 추가한다(C의 `replyTo`).
- `adapter/out/llm/ClaudeSuggestionAdapter`: LLM 호출. 생성자에서 설정값만 주입받고 네트워크 호출은 하지 않는다(키 없는 CI에서도 빌드 가능, `NaverClovaVoiceAdapter`와 같은 방식).
- `adapter/in/web/PhraseSuggestionController`, `dto/`
- 설정: `voicebridge.suggestion.*`(모델 ID, 타임아웃, 후보 개수 상한). 키는 `ANTHROPIC_API_KEY` 환경변수(공식 SDK 기본 이름, 배포는 Secrets Manager `voicebridge/dev/app`).

### 3.3 규칙과 안전장치

- **후보 개수 상한 5개, 후보 길이 상한은 문구 규칙(`Phrase`)을 그대로 재사용한다.** 검증값은 도메인에만 둔다(SSOT).
- LLM 출력은 **JSON 배열만 허용**한다. 파싱 실패, 빈 배열, 제어문자는 걸러내고, 전부 걸러지면 503으로 처리한다.
- **프롬프트는 사용자가 입력한 텍스트를 지시문이 아닌 데이터로 취급하도록 분리한다.** 입력에 "이전 지시를 무시해"가 들어 있어도 후보 형식을 바꾸지 못해야 한다.
- 시스템 프롬프트에 "사용자가 직접 말할 법한 1인칭 요청·의사 표현 문장만, 의료 조언·진단·복용량 판단 금지"를 명시한다. 프롬프트로 완전히 막을 수 없으므로 최종 선택은 사용자가 한다.
- **호출 상한(비용·남용 방어)**: 사용자별 분당 호출 수 제한. Redis가 이미 필수 인프라이므로 카운터로 구현한다. 상한값은 정책값(예: 분당 10회, 확정 필요).
- 입력 텍스트와 응답은 로그에 남기지 않는다.

### 3.4 에러코드(추가)

`SUGGESTION_UNAVAILABLE`(503), `TOO_MANY_REQUESTS`(429)

### 3.5 LLM 선택

| 후보 | 장점 | 단점 / 미확인 |
| --- | --- | --- |
| **Claude API, Haiku급** (`claude-haiku-5-5`) | 응답이 빠르고 JSON 형식 출력이 안정적 | 요금·한도는 구현 전 확인 필요 |
| Claude API, Sonnet급 (`claude-sonnet-5-5`) | 후보 품질이 더 좋을 수 있음 | 지연이 더 김. 버튼을 누르고 기다리는 화면엔 부담 |
| HyperCLOVA X (CLOVA Studio) | 한국어, 클로바와 같은 벤더·청구 | 이 문서 작성 시 조사하지 않음. **미확인** |

**기본값은 Haiku급으로 하되 포트로 감싸서 교체 가능하게 둔다.** 확정 전에 실제 문장 20개 정도(병원·식당·일상 짧은 말)로 후보 품질을 팀이 눈으로 비교한다.

### 3.6 테스트

- 도메인·검증 단위: 후보 필터링(개수, 길이, 중복, 제어문자), 프롬프트 입력 분리.
- 어댑터: WireMock으로 LLM 응답 계약 테스트(정상 / 형식 깨짐 / 타임아웃 / 5xx → 503).
- 통합(MockMvc): 정상 200, 플래그 꺼짐 404, 미인증 401, 호출 상한 초과 429, 후보 저장 없음 확인.
- Mock 통과는 실제 LLM 동작을 보장하지 않는다. 실제 키로 샘플 입력 20개를 수동 점검한다.

## 4. 기능 C — 대화 모드

### 4.1 흐름

1. 상대의 말을 녹음해 서버로 보낸다 → 음성인식으로 텍스트화.
2. LLM이 그 텍스트에 대한 **답변 후보**를 만든다.
3. 화면에 "들은 말"과 후보를 보여준다 → 사용자가 후보를 누른다.
4. TTS가 대신 대답한다.

### 4.1-1 사용자의 답변 방식 (화면에서 고른다)

| 방식 | 흐름 | 백엔드 |
| --- | --- | --- |
| 후보 누르기 | 후보 선택 → speak(4.2) | 이 기능에서 신규(C-2) |
| 말하기 | 녹음 → `POST /recognitions` → 결과를 보고 고침 → `/confirm` → `POST /tts` | **새 코드 없음.** 기존 인식 흐름 재사용 |
| 문구함 | 문구 선택 → 문구 말하기(PIVOT PR 3) | 새 코드 없음 |

- "말하기"는 우리가 학습시킨 모델이 아니다. 개인화를 제외했으므로 AI 서버의 **기본 Whisper-small(적응 없음)**이 인식한다. AI 팀 측정으로 기본 모델도 화자군에 따라 자모 오류율이 2~52%로 벌어지고(large-v3 기준, 우리가 쓰는 small은 평균 오류율이 더 높다), 그래서 **인식 결과를 그대로 말하지 않고 항상 사용자가 보고 고친 뒤에만 TTS**를 한다(기존 확인 규칙).
- AI 서버는 배포돼 있다(2026-10-30 백엔드 EC2에서 `GET /v1/health` 확인: `ai-contract-v1`, 엔진 `transformers+peft`, `openai/whisper-small` revision `973afd2496…`(검증됨), 어댑터 없음). 다만 한 번에 한 요청만 처리하므로(CPU, 첫 요청 약 4초, 이후 약 0.7초, 백엔드 읽기 타임아웃 10초) 요청이 몰리면 "말하기"가 503이 될 수 있다. 실제 녹음 인식 왕복은 아직 확인 전이다. local은 스텁이다. 후보 누르기와 문구함은 영향이 없다. 프론트는 인식 503을 받으면 "말하기를 지금 사용할 수 없어요. 후보나 문구를 이용해 주세요"로 안내한다.
- v2(이번 범위 제외): 사용자가 말한 인식 결과와 상대의 들은 말을 함께 LLM에 줘서 후보를 보정할 수 있다. 이때도 "내가 말한 그대로"를 첫 번째 선택지로 둔다.

### 4.2 API

| 메서드 | 경로 | 설명 |
| --- | --- | --- |
| POST | `/conversation/turns` | multipart 음성 → `{turnId, heardText, candidates:[{id, text}]}` |
| POST | `/conversation/turns/{turnId}/candidates/{candidateId}/speak` | 선택한 후보를 TTS로 합성해 `audio/mpeg`로 응답 |

- **임의의 텍스트를 TTS로 만들어주는 엔드포인트는 만들지 않는다.** 그러면 우리 서버가 누구나 쓰는 무료 TTS 프록시가 되어 비용이 새고, "확인된 문장만 말한다" 원칙도 깨진다. 서버가 이번 턴에 발급한 후보 ID만 말할 수 있다.
- speak 응답은 저장소에 올리지 않고 오디오 바이트를 그대로 돌려준다(`Cache-Control: no-store`). 파일이 남지 않아 S3 정리 문제가 없다.
- 턴은 **Redis에 짧은 TTL(예: 10분, 정책값)로만** 둔다. 들은 말·후보·원본 음성은 DB에 저장하지 않는다.
- 소유권: 턴에 `userId`를 저장하고 다른 사용자의 `turnId`는 거부한다. 만료되었거나 없는 턴/후보는 404.

### 4.3 구성

- `port/out/SpeechToTextPort`: `String transcribe(byte[] wavBytes)` — 외부 STT 호출
- `port/out/LlmSuggestionPort.replyTo(heardText)` (B와 공유)
- `port/out/ConversationTurnStorePort`: 턴 저장·조회(Redis, TTL)
- `adapter/out/stt/NaverClovaSpeechAdapter`, `adapter/out/persistence` 또는 `adapter/out/cache`의 Redis 구현
- 오디오 입력은 `AudioNormalizationPort`(FFmpeg 16kHz 정규화)를 인식 때와 똑같이 재사용한다. 길이 상한(0.3~30초)과 오디오 오류 코드도 동일.
- 플래그 `voicebridge.features.conversation`(기본 꺼짐), 호출 상한은 B와 같은 방식.
- 에러코드 추가: `STT_UNAVAILABLE`(503)

### 4.4 어떤 API를 쓸까

| 역할 | 추천 | 이유 |
| --- | --- | --- |
| **음성인식(상대의 말)** | **네이버 클라우드 CLOVA Speech Recognition (CSR)** | 이미 클로바 보이스 TTS로 같은 클라우드를 쓰고 있고, 헤더 방식(`X-NCP-APIGW-API-KEY-ID`/`X-NCP-APIGW-API-KEY`)과 어댑터 패턴이 같다. 한국어 중심이고 요청은 짧은 음성을 바이너리로 보내는 동기 방식이다 |
| 답변 후보 | LLM (3.5와 같은 포트) | 후보는 의료·일상 맥락의 짧은 문장이다 |
| 대신 말하기 | 클로바 보이스(기존) | 새로 추가할 것 없음 |

CSR에 대해 확인한 것 (네이버 클라우드 공식 문서와 검색 결과 기준, 2026-10-30)
- 현행 서비스로 문서화돼 있고 종료 공지는 찾지 못했다. 최근 릴리스 노트(2026-07-23)에 기능 변경이 있다.
- 공식 문서는 CSR을 **"1분 이내의 명령형 음성 인식에 최적화"**라고 설명한다. 우리 입력 상한(30초)보다는 넉넉하다.
- 콘솔에서 Application을 만들 때 **CLOVA Speech Recognition을 선택하지 않으면 429가 난다.** TTS용 Application에 CSR 서비스를 추가해서 같은 키를 쓸 수 있는지는 콘솔에서 확인해야 한다(**미확인**).
- 릴리스 노트에 스트리밍 인식 항목이 있어 실시간 인식도 지원하는 것으로 보이지만, 이번 범위(턴 방식 동기 호출)에는 필요 없다.
- **의사·간호사의 일상 대화나 의학 용어에 대한 정확도는 측정된 게 없다.** "명령형에 최적화"라는 설명이 걸린다. 실제 키로 병원 상황 문장 20개를 읽어 녹음해 확인한 뒤 확정한다.

대안
- **자체 AI 서버의 기본 Whisper 모델**(`use_adapter=false`): 새 벤더 없이 `AiInferenceClient`를 재사용할 수 있다. AI 서버는 배포돼 있지만(2026-10-30 확인) 한 번에 한 요청만 처리하고, 대화 모드가 같은 서버를 쓰면 사용자 "말하기" 인식과 순서를 다투며, small 모델이라 일반 화자 정확도가 CSR보다 낫다는 근거가 없다. CSR이 기대에 못 미칠 때의 대체안으로 둔다.
- 해외 음성인식 API: 한국어 품질은 좋을 수 있지만 계정·키가 늘고 의료 상황 음성이 해외로 나간다. 지금은 추천하지 않는다.

### 4.5 안전 설계 (병원 상황은 오해의 비용이 크다)

- 화면에 **들은 말을 가장 크게** 보여준다. 인식이 틀렸다는 걸 사용자가 바로 알아야 한다. "다시 듣기(재녹음)" 버튼을 둔다.
- "약을 드시겠어요?" 같은 질문에도 후보에 **예/아니요 두 방향을 모두** 포함시킨다(프롬프트 규칙).
- 동의나 결정을 뜻하는 후보는 한 번 더 확인하게 하는 UX를 제안한다(프론트 판단).
- 상대의 말에 지시문이 섞여 있어도 후보 형식을 바꾸지 못하게 한다. **들은 말은 신뢰할 수 없는 입력이다.**
- 상대 목소리를 녹음하는 기능이라 **동의·고지 문구와 법적 검토가 필요하다.** 우리가 법적 판단을 하지 않고, 서버는 음성을 저장하지 않는다는 점만 보장한다.

### 4.6 예상 지연 (측정 전 추정)

STT, LLM, TTS가 직렬이라 한 턴에 몇 초가 걸릴 수 있다. 실제 값은 구현 후 측정한다. 느리면 후보를 먼저 보여주고 TTS는 선택 후에 합성하는 현재 구조를 유지하면 체감이 줄어든다.

### 4.7 테스트

- 어댑터: WireMock으로 CSR·LLM 계약 테스트(정상 / 빈 인식 / 타임아웃 / 5xx → 503).
- 통합: 턴 생성 200, 후보 선택 → TTS 200(`audio/mpeg`).
- **우회 차단을 따로 증명**: 다른 사용자의 `turnId` 거부, 만료된 턴 404, 위조된 `candidateId` 404, 임의 텍스트로 TTS 불가, 플래그 꺼짐 404, 미인증 401, 호출 상한 초과 429.
- 음성이 서버 저장소에 남지 않는지 확인하는 테스트.
- 실제 CSR·LLM·클로바로 **수동 E2E 한 번**(병원 대화 샘플 20개).
