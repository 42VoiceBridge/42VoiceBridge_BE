## 설계에서 먼저 바로잡을 계약

1. **문장 식별자:** 기존 업로드 포트는 `UUID sentenceId`지만 추천은 문자열 `promptId`다. 개인화 요청은 `promptId` 기준으로 바꾸고 API 4.1과 DTO/포트를 함께 수정하는 안을 권장한다. 실제 FE 사용 여부를 확인해 필드 변경을 조율한다. 진단 UUID로 강제 변환하지 않는다. `promptId`만으로 중복 추천의 원문을 특정할 수 없으므로 추천 응답에 `shownPromptId`(기존 추천 기록 UUID)를 추가하고 업로드에서 함께 받는 안을 기본으로 한다. 사용자·`shownPromptId`·`promptId` 일치를 검증하고 “최신 추천”으로 임의 연결하지 않는다. API 3.1과 추천 DTO/포트도 Goal A 변경 범위에 포함한다.
2. **학습 데이터의 정답:** 사용자에게 제안했던 문장 원문과 추천 기록 ID를 서버에서 가져와 보존한다. 같은 prompt가 여러 번 제안될 수 있으므로 어떤 추천 기록을 연결할지도 정한다. 제안 기록은 화면 표시·실제 낭독·정답 검토의 증거가 아니다. 문장 풀 버전이 제공되지 않으면 미확인으로 기록하며 전략 버전을 풀 버전으로 대체하지 않는다. 검토된 낭독 정답과 버전이 없는 녹음은 수동 export나 학습 대상에서 제외한다.
3. **동의·보관:** 보관 동의와 학습 사용 동의를 구분하고 둘 다 명시적인 boolean으로 받는다. multipart의 `metadata` JSON 파트(`Content-Type: application/json`)에 문장 식별자와 동의 필드를 두는 안을 기본으로 한다. 동의 필드 생략은 `false`, 전달된 값은 JSON boolean만 허용하고 null·문자열·숫자는 거절한다. Jackson의 문자열→boolean 강제 변환을 막고 HTTP 테스트로 검증한다. 보관 동의가 false이면 영구 파일/녹음 행을 만들지 않고 400 `VALIDATION_FAILED`로 거절한다. 보관 true·학습 false는 201로 저장하되 학습 대상에서 제외한다. 동의 값·정책 버전·수신 시각을 보존한다. 보관/삭제 기간과 철회 후 처리 정책은 구현 전에 API 계약으로 확정한다.
4. **학습 지원:** 전달 문서상 AI 온라인 train은 501, job 조회는 404다. 실제 학습 goal은 AI 계약과 접근 가능한 서버가 준비된 뒤 시작한다. 가짜 완료 job이나 202 응답만으로 학습 구현을 완료 처리하지 않는다.
5. **학습 기준:** 현재 최소 5개는 도메인의 임시 정책이다. 초기 구현에서는 유지하되 품질 기준으로 주장하지 않는다. 어떤 녹음을 학습 대상으로 인정할지와 동일 문장 재녹음 선택 규칙을 명세화한다.

## Goal A — 개인화 녹음 업로드 완성

### 착수 조건

문장 ID·동의·보관 계약을 확정한다. 로드맵의 확인·동의 API(P06; 참조 문서상 미착수)와 충돌하지 않도록 계약을 점검한다. 새로운 `origin/develop` 기준의 격리된 브랜치에서 시작하고 기존 작업 트리 변경을 보존한다. 권장 브랜치: `feature/personalization-recording-ingest`.

### 구현 순서

1. API 3.1/4.1, 추천·업로드 요청/응답 DTO, inbound port를 함께 정의한다. 201의 data는 `{recordingId, status: UPLOADED}`이며 실제 응답은 공통 `ApiResponse` envelope를 사용한다. 기존 요청과의 호환/전환 방식을 FE와 확정한다.
2. 개인화 녹음 도메인과 repository port/JPA adapter를 추가한다. 진단 세션 소속 녹음과 생명주기가 달라 별도 모델을 사용한다. 사용자, 추천 기록/문장 ID, 원문, 저장 키, 동의, 변환 메타데이터, 생성 시각을 보존한다.
3. `ShownPromptRepositoryPort`에 사용자와 추천 기록을 확인할 조회를 추가한다. `shownPromptId`로 단일 기록을 특정하고 원문은 클라이언트가 임의로 지정하지 못하게 한다.
4. 기존 `AudioNormalizationPort`와 `StoragePort`를 재사용한다. 저장 후 DB 실패 시 파일을 지울 수 있도록 `StoragePort`에 삭제 연산을 추가하고 로컬/S3 구현을 검증한다. 외부 저장 작업은 DB 트랜잭션 밖에서 수행한다. 정규화된 바이트는 `.wav` 키로 저장한다. 현재 `upload()`는 내부에서 임의 키를 생성하므로 실패한 호출의 키를 호출자가 알 수 없다. 사전 발급한 키로 저장하는 port 연산과 멱등 삭제를 추가하고, 저장 전 영속화한 업로드 시도 기록으로 재시작 후에도 정리 대상을 추적한다. 성공한 녹음만 `UPLOADED`로 공개한다. DB 커밋 결과가 불명확하면 성공 행 존재를 확인한 뒤 삭제하고, 삭제 실패는 재시도 대상으로 남긴다. 로컬 삭제는 저장 루트 밖 경로를 거절한다. 기존 StoragePort 호출자 호환성도 검증한다.
5. 업로드 서비스와 컨트롤러를 연결하고 공통 예외 응답으로 번역한다. 공개 상태·오류 코드는 API 0.6/4.1 및 변경 이력에 기록한다.
6. 스키마 DDL/적용 방법, 요청 예제, 검증 결과를 문서화한다. 보관 만료·철회 시 적격성 차단 및 파일 삭제를 수행할 인증된 운영 경로와 재시도 절차까지 구현한다. 단순 정책 문서만으로 실제 삭제를 대체하지 않는다.
7. 오류 표를 확정한다. 기존 정규화 정책의 잘못된 음성/크기 초과는 400 `VALIDATION_FAILED`, 처리 용량/시간 초과는 503 `AUDIO_PROCESSING_UNAVAILABLE`, 도구·저장소 장애는 500 `INTERNAL_SERVER_ERROR`를 재사용한다. 인증·소유권·없는 추천·잘못된 JSON/파트 Content-Type도 상태/코드를 명시하고 MVC 테스트한다. AI 내부 오류 코드를 그대로 공개하지 않는다.

- [ ] 인증 사용자가 본인에게 제안된 문장, 명시적 동의, 유효 음성을 보내면 201이며 DB와 저장소에 일치하는 녹음이 생성된다. 이 시점의 상태는 `UPLOADED`이며 검토·학습 완료를 의미하지 않는다.

## Goal B — 수동 학습 전달물 생성

온라인 학습 API가 없는 현재, 업로드 다음의 실행 가능한 단계다. 별도 goal로 두어 Goal A의 업로드 201을 학습 가능 상태로 오해하지 않게 한다.

### 착수 조건

- Goal A 완료. 학습용 정답 검토 절차, 문장 풀 버전 확보 방식, 데이터 삭제/동의 철회 처리, AI 담당과의 전달 형식이 확정돼 있다.

### 구현 및 완료 조건

1. 사용자가 검토한 실제 낭독 정답과 해당 버전, 명시적 학습 동의를 녹음과 연결한다. 단순 추천 기록이나 확인된 발신 문장을 자동으로 정답 처리하지 않는다.
2. 오프라인 학습용 스냅샷/manifest를 만든다. 녹음 ID·해시·WAV 위치, 검토된 정답과 버전, 문장 ID·원문·풀 버전, 변환 버전, 동의 상태를 기록한다. 누락·철회된 데이터는 제외한다. 녹음의 train/dev/test 분할을 고정하고 test는 학습·승격 판단에서 제외한다. 소비 측과 스키마 버전 및 필수 필드를 합의한다. 저장 키는 AI가 읽을 수 있는 위치가 아니므로 별도 읽기/전달 port와 접근 수단을 구현한다. 정규화 WAV와 해시를 대조하며 서버 내부 경로나 영구 공개 URL을 전달하지 않는다.
3. 권한 있는 실행 경로로만 export한다. 민감 음성의 전달·접근·삭제 절차를 문서화하고 API 변경 시 `.codex/context/API.md`도 갱신한다.
4. 실제 샘플을 export해 AI 측 소비 형식으로 읽히는지 확인하고 결과와 접근 통제 테스트를 남긴다. 전달 직전 동의를 재확인하고, 전달 후 철회는 manifest ID/녹음 ID로 추적해 수신 측 삭제 확인을 기록한다. 이 검증이 끝나야 complete다.

이 goal도 학습 완료나 adapter 활성화를 뜻하지 않는다.

## Goal C — 실제 개인화 학습 흐름 완성 (외부 선행조건 충족 후)

### 착수 조건

- Goal A 및 Goal B의 공통 데이터 요건(정답 검토·버전·동의·분할·스냅샷) 완료. 수동 export 도구 자체는 온라인 학습의 필수 선행조건이 아니다. 온라인 API가 먼저 준비되면 공통 요건을 구현하고 Goal B의 수동 전달 단계는 건너뛸 수 있다.
- 실제 AI train/job API가 제공되고 요청 형식, 데이터 전달 방식, job ID, 상태·진행률·오류, 멱등성, 타임아웃 계약이 확정돼 있다.
- 테스트용 AI 서버와 학습 가능한 데이터에 접근할 수 있다. 충족되지 않으면 이 goal을 시작하지 않고 미착수 사유를 기록한다.

권장 브랜치: `feature/personalization-training-orchestration`.

### 구현 순서

1. 별도 학습 outbound port와 HTTP adapter를 만든다. 기존 인식 포트에 HTTP DTO를 노출하지 않는다.
2. 사용자 본인의 동의·검토 요건을 충족한 녹음으로 불변 학습 입력 스냅샷을 만들고 job에 연결한다. 최소 개수는 이 스냅샷의 실제 train 분할로 판단한다. 동일 문장 재녹음은 검토·동의 요건을 만족하는 최신 녹음을 선택하고 동률 처리 기준까지 고정한다. API 4.2의 “업로드 전체 사용” 설명을 적격성·중복 선택·분할 규칙으로 갱신한다. 기본 모델 revision·학습 설정·seed도 스냅샷에 보존한다.
3. 동일 사용자 요청을 DB 수준에서 직렬화해 진행 중 job을 하나로 제한한다. 단순 `findInProgress` 후 INSERT만으로 동시성을 처리하지 않는다.
4. PENDING을 저장한 후 커밋된 job을 AI에 제출한다. 외부 호출 중 DB 잠금을 유지하지 않는다. job과 제출 outbox를 같은 트랜잭션에 저장하고 worker가 내구성 있는 재시도를 수행한다. BE job ID를 제출 멱등 키로 사용하고 AI job ID를 별도로 보존한다. AI가 요청을 받았으나 응답이 유실된 경우 같은 키로 조회/재전송해 중복 생성을 막는 계약이 필요하다. 제출 직전에 철회를 재확인하고 이미 제출된 데이터의 철회/취소 처리도 정의한다.
5. 상태 동기화로 PENDING → IN_PROGRESS → COMPLETED/FAILED를 영속화한다. 현재 job/JPA에는 AI job ID·진행률·재시도 정보·동시 갱신 버전이 없으므로 추가한다. 중복/역순 상태 응답으로 terminal 상태가 되돌아가지 않게 하고, 즉시 완료·실패 및 PENDING 제출 실패도 처리한다. AI가 진행률을 제공하지 않으면 추정값을 만들지 않고 nullable 계약으로 API 4.3을 갱신한다.
6. 학습 산출물 완료와 실제 serving adapter 활성 상태를 구분한다. 학습 완료만으로 실사용 인식의 `modelUsed`를 PERSONALIZED로 단정하는 기존 동작을 수정한다.

### 완료 조건 — 전부 만족해야 complete

- [ ] 적격 녹음 부족은 422 `INSUFFICIENT_RECORDINGS`, 진행 중 중복 요청은 409 `INVALID_STATE_TRANSITION`이다.
- [ ] 같은 사용자 동시 요청에서 활성 job 및 AI 학습이 하나만 생성됨을 실제 MySQL 경합 테스트와 제출 멱등성 테스트로 증명한다.
- [ ] 정상 요청은 202와 실제 저장된 job ID를 반환하고 GET에서 상태 변화가 확인된다.
- [ ] AI 성공·실패·타임아웃·계약 위반·프로세스 재시작을 검증하며 job이 무기한 대기하지 않는다. 재시도 횟수/기한과 최종 실패 사유가 명세화돼 있다.
- [ ] 다른 사용자 job 접근은 차단되고, 동의 없는/다른 사용자 녹음은 학습 입력에 포함되지 않는다.
- [ ] 실제 AI 환경에서 업로드 → 학습 접수 → 완료/실패 조회를 실행하고 증거를 남긴다. 스텁 테스트만으로 대체하지 않는다.
- [ ] 완료 산출물의 모델/버전 식별 정보가 저장되고, 활성화되지 않은 산출물을 실제 사용 모델이라고 표시하지 않는다. 학습 완료와 adapter 설치·검증·활성화는 서로 다른 상태임을 응답과 저장 모델에 반영한다.
- [ ] 전체 테스트·Spotless·영향받는 오디오 통합 테스트가 통과하고 API 0.6/4.2~4.4/관련 인식 응답 및 변경 이력, DDL이 갱신돼 있다.

범위 밖: 모델 품질 향상 보장, 자동 승격·롤백 시스템, AI 학습 서버 자체 구현, 운영 배포. 실제 AI 의존성이 도중에 사라지면 남은 조건을 기록하며 complete로 처리하지 않는다. 기존 인식의 잘못된 모델 표시 수정은 이 goal에 포함하되, 별도 P04 작업으로 먼저 완료됐으면 그 결과를 검증해 재사용한다.

## 나중에 goal을 시작할 때 사용할 요청문

> docs/ENDPOINT-IMPLEMENTATION-PLAN-2026-09-30.md의 Goal A를 수행하는 goal을 생성하고 실행해줘. 최신 origin/develop의 변경을 먼저 확인하고, 기존 미커밋 변경을 보존한 별도 작업 공간에서 진행해. 착수 조건의 미확정 계약은 먼저 확인하고, 구현·명세·DDL·필수 검증을 모두 완료해. Goal A의 체크리스트를 전부 만족했을 때만 complete로 처리하고, 최종 답변에는 각 조건의 검증 근거와 남은 제한을 적어줘. Goal B/C와 merge·배포는 포함하지 마.

Goal B는 데이터 전달 계약이 정해진 후, Goal C는 공통 데이터 요건과 실제 AI 학습 API가 준비된 후 별도 goal로 시작한다. 이번 문서는 계획이며 goal 실행은 시작하지 않았다.
